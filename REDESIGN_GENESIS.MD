# Анализ и предложения по развитию genesis

Документ состоит из двух частей: что выявлено при анализе проекта и что предлагается изменить. Анализ выполнен по состоянию ветки `main` на коммит `13df32d`; номера строк в тексте относятся к этому коммиту.

## Коротко

- Архитектура ядра удачная: состояние, метрика, алгоритм, селектор точек и критерий остановки — независимые детали, которые комбинируются между собой.
- Найдено семь ошибок в алгоритмах, каждая воспроизведена запуском. Самая серьёзная: имитация отжига неверно работает с максимизируемыми метриками (индекс прикрытия) и превращается в случайное блуждание.
- Набор тестов не запускается целиком из-за одного неверного импорта.
- Главный резерв скорости — оценивать решения по заранее посчитанной матрице времён прибытия, а не запускать алгоритм Дейкстры на каждую оценку.
- Задачи покрытия (MCLP, LSCP) можно решать точно готовыми решателями; сейчас нет способа узнать, насколько эвристики далеки от оптимума.
- Индекс прикрытия считается только по достижимым объектам: расстановка, оставляющая полгорода без прикрытия, получает 100 %.
- Ноутбуки с экспериментами для диссертации не запускаются на текущем коде, а имитация отжига в них работала с максимизируемой метрикой, то есть с ошибкой.
- Два примера из документации на текущем коде не работают: один падает, другой молча возвращает пустой результат.

## Как проводился анализ

Прочитан весь код пакетов `genesis`, `fire_units`, `graphs`, `lists`, тесты, конфигурация документации и архив плагина QGIS.

Ноутбуков в репозитории 78. По всем выполнены автоматические проверки: импорты, секреты, абсолютные пути, сохранённые ошибки, фиксация `seed`. Полностью прочитаны ноутбуки документации для пользователей и разработчиков и основные исследовательские (`dis_algorithms*`, `add_check`, `dis_optimums_area`, `lscp_build_for_qgis`, `grid_graphs_test` и восемь небольших). Черновики из `temps/`, архивные ноутбуки, `g_generator` и учебные страницы про `osmnx` и `geopandas` просмотрены по структуре ячеек, не построчно.

Тесты и проверки ошибок запускались в окружении: macOS, Python 3.12, `osmnx` 2.0.0, `networkx` 3.4.2, `pandas` 2.2.2, `numpy` 2.0.2, `geopandas` 1.0.1 — версии взяты из `genesis_env.yaml`. Скрипт, воспроизводящий ошибки, приведён в приложении.

# Часть 1. Результаты анализа

## 1.1. Сильные стороны

- **Модульность.** `BestNodesKoptG` принимает любой алгоритм BLP, `LSCPCommon` — любой MCLP, селектор и критерий остановки, `Hybridization` склеивает алгоритмы в цепочку. Новую метрику или селектор можно добавить, не трогая остальное.
- **Направление оптимизации спрятано в метрике.** Метод `compare` знает, минимизируется метрика или максимизируется, и большинство алгоритмов от этого не зависят.
- **Учтены реальные условия.** Существующие подразделения фиксируются через `static_nodes`, есть маска расчётной области `area` и допуск `appr_val` на слабосвязанные узлы графов OSM.
- **Заделы на скорость.** Матрица времён прибытия с расчётом батчами (`get_atm`) и кэш для неподвижных подразделений (`FirstArrivalUnitCacheState`).
- **Предметные данные.** Скорости пожарных автомобилей из собственного исследования, справочник классов функциональной пожарной опасности с коэффициентами спроса.
- **Обратные вызовы** после эпох и итераций — удобно для прогресса и для плагина QGIS.
- **Проверка входных данных** с понятными сообщениями.
- **Документация** в виде книги с разделами для пользователей и разработчиков, файл соглашений об именах, канбан-доска в репозитории.
- **Генератор синтетических графов** для сравнения алгоритмов в контролируемых условиях.

## 1.4. Тесты

Результат прогона: из 82 тестов 77 прошли, 1 упал, 1 помечен как ожидаемо падающий, 3 не запустились. Прогон занимает около полутора минут.

- **Набор не запускается целиком.** `tests/test_adapters.py:20` импортирует `AdapterBLP2MCLP` из `genesis.mclp`, а класс находится в `genesis.hybridisation`. Команда `pytest tests` останавливается на этой ошибке, не выполнив ни одного теста. С исправленным импортом все три теста файла проходят.

- 31 проверка сравнивает числа с плавающей точкой через `==`. На версиях из `genesis_env.yaml` все они прошли, но при обновлении `networkx` или `osmnx` могут сломаться.

## 1.6. Производительность

- Каждая оценка решения в `BestNodesGA`, `BestNodesSA` и алгоритмах BLP — полный алгоритм Дейкстры на чистом Python. `nx.multi_source_dijkstra` при этом строит полный путь до каждого узла, а используется из него только первый элемент.
- Генетический алгоритм пересчитывает одинаковых особей: стартовая популяция — N копий одного решения, каждая оценивается отдельно; элита переоценивается каждую эпоху.
- `BestNodeMonkey` на каждом глобальном прыжке заново переводит граф в GeoDataFrame и перепроецирует его (`genesis/best_points.py:717-719`). Два теста этого алгоритма занимают по 20 секунд — половину всего времени прогона.
- `BestNodesKoptG` копирует подграф на каждое подразделение в каждой итерации.
- `get_atm` склеивает матрицу через `pd.concat` в цикле.
- `CoverIndex` считает долю циклом Python по элементам.

### По чтению кода (данные недоступны, запуском не проверялось)

**Эксперименты для диссертации** (`dis_algorithms.ipynb`, `dis_algorithms copy.ipynb`, `dis_algorithms IPV5.ipynb`):

- Имитация отжига запускается с максимизируемой метрикой: в ранних версиях это `Demand` (`comp_func=max`), в `IPV5` — `CoverIndexValue`. Формула вероятности перехода в `genesis/mclp.py` не менялась с 05.07.2024, ноутбуки появились 13.08.2024. Значит, результаты SA в сравнении алгоритмов BLP и MCLP получены с ошибкой № 1 и требуют пересчёта.
- В сравнении MCLP каждый стохастический алгоритм запускается по одному разу на район, без фиксации `seed`.
- Столбец «точность» в таблице BLP имеет разный смысл для разных алгоритмов: для HC, MSA, ABC это доля запусков, попавших в эталонный узел, для HC+BNHD и SA — отношение метрики к эталонной.
- В эксперименте LSCP число подразделений и время берутся из лучшего запуска, а метрика — из последнего.
- В `dis_algorithms.ipynb` (ячейка 27) библиотечная `drop_trash_points` переопределена локальной версией с пометкой «Потом удалить!». Она оценивает набор до удаления очередной точки, а не после, и поэтому удаляет на одну точку больше, чем позволяет критерий. Сохранённая таблица результатов взята из кэша, и метрики в ней не ниже целевых, то есть получена она, по-видимому, другой версией; при пересчёте без кэша результат изменится.

**Оценка точности ADD** (`add_check.ipynb`):

- Точность оценивается сравнением числа подразделений до и после `drop_trash_points`, то есть с собственным же результатом, а не с оптимумом.
- Города, на которых расчёт упал, пропускаются через `except Exception: print(e)`; в итоговой таблице их просто нет.
- Выборка зданий случайная, без `seed`.

**Прочее:**

## 2.2. Производительность

**Оценивать решения по матрице, а не по графу.** Это главный рычаг.

Сейчас метаэвристики на каждую оценку запускают алгоритм Дейкстры. Если один раз посчитать матрицу «кандидат × объект» (`get_atm` уже есть), оценка любой расстановки становится минимумом по нескольким столбцам — одной операцией `numpy`. Класс `ArrivalTimeMatrixState` для этого уже существует; его нужно снять с пометки «устаревшее», покрыть тестами и сделать основным способом оценки в `BestNodesGA` и `BestNodesSA`.

Дополнительно при перестановке одного подразделения можно не пересчитывать всё: достаточно хранить для каждого объекта лучшее и второе по времени подразделение.

**Считать по уникальным узлам (Н6).** Сейчас `get_atm` запускает расчёт для каждого здания. Достаточно одного расчёта на узел с последующим разворачиванием на здания; на тестовых данных это втрое меньше работы без каких-либо других изменений.

**Считать матрицу не на `networkx`.** `scipy.sparse.csgraph.dijkstra` выполняет тот же расчёт на C, поддерживает ограничение по дальности (`limit`) и считает несколько источников за вызов. Граф переводится в разреженную матрицу один раз. Ориентир для сравнения есть в `atm_transpose_avoid.ipynb`: матрица для Красноярска сейчас считается 1 час 36 минут и занимает до 19,5 ГБ.

**Ограничить размер матрицы.** Полная матрица для графа в 50 тысяч узлов занимает около 20 ГБ. Два способа:

- хранить только пары в пределах порога прибытия — разреженная матрица, для задач покрытия этого достаточно;
- сократить список кандидатов до мест, где депо реально можно разместить.

**Убрать повторные вычисления:** кэш приспособленности по набору узлов в генетическом алгоритме, однократное проецирование узлов в `BestNodeMonkey`, векторный расчёт в `CoverIndex`, сборка матрицы в `get_atm` одним `concat` в конце.

**Распараллелить независимые оценки** — особей в популяции, кандидатов в полном переборе.

Перед началом работ нужен бенчмарк на тестовом графе: время одной оценки решения и время полного расчёта для каждого алгоритма. Без него нельзя сказать, какое ускорение даёт каждое изменение.

## 2.3. Алгоритмы

**Точное решение задач покрытия.** MCLP и LSCP — задачи целочисленного линейного программирования. Пусть `x_j = 1`, если в кандидате `j` размещено подразделение, `y_i = 1`, если объект `i` прикрыт, `N_i` — кандидаты, из которых до объекта `i` успевают за пороговое время, `w_i` — вес объекта.

LSCP (минимум подразделений при полном прикрытии):

```
min  Σ_j x_j
при  Σ_{j ∈ N_i} x_j ≥ 1   для каждого объекта i
```

MCLP (максимум прикрытия при `p` подразделениях):

```
max  Σ_i w_i · y_i
при  y_i ≤ Σ_{j ∈ N_i} x_j   для каждого объекта i
     Σ_j x_j = p
```

Существующие подразделения задаются условием `x_j = 1`. Множества `N_i` получаются из матрицы времён прибытия. Решатели — HiGHS (`scipy.optimize.milp`) или OR-Tools — выдают оптимум либо гарантированный разрыв до него.

Это даёт эталон для эвристик: сейчас нет способа узнать, насколько результат генетического алгоритма далёк от оптимума. Ограничение: формулировка подходит для метрик покрытия. Для среднего времени прибытия (задача p-медианы) модель крупнее, и на больших графах эвристики останутся нужны.

**Обменный локальный поиск для среднего времени.** `BestNodesKoptG` по сути является алгоритмом Маранзаны: каждое подразделение переставляется в лучшую точку своей зоны. Алгоритм Тейца–Барта (убрать одну точку, поставить другую, принять обмен при улучшении) для p-медианы обычно даёт лучшие решения и по матрице считается быстро. Его стоит добавить как отдельный MCLP-алгоритм и как финальную доводку после генетического.

**Усиление жадного добавления.** Функция покрытия субмодулярна, поэтому жадный алгоритм для MCLP гарантирует результат не хуже 63 % от оптимума, а «ленивый» вариант даёт тот же результат за меньшее число пересчётов. После жадного добавления стоит выполнять шаг замены.

**Доработка метаэвристик** помимо исправления ошибок:

- разнообразная стартовая популяция в генетическом алгоритме вместо N копий одного решения;
- шкала температуры в отжиге, учитывающая масштаб метрики (минуты и проценты сейчас обрабатываются одинаково);
