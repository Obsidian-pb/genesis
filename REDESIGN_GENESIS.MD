# Анализ и предложения по развитию genesis

Документ состоит из двух частей: что выявлено при анализе проекта и что предлагается изменить. Анализ выполнен по состоянию ветки `main` на коммит `13df32d`; номера строк в тексте относятся к этому коммиту.

Предложения по производительности и алгоритмам (разделы 2.2, 2.3 и план в 2.8) опираются на измерения из `EXPERIMENTS_GENESIS.MD`: три эксперимента на тестовом графе Сосновоборска и один на графе Красноярска.

## Коротко

- Архитектура ядра удачная: состояние, метрика, алгоритм, селектор точек и критерий остановки — независимые детали, которые комбинируются между собой.
- Найдено семь ошибок в алгоритмах, каждая воспроизведена запуском. Самая серьёзная: имитация отжига неверно работает с максимизируемыми метриками (индекс прикрытия) и превращается в случайное блуждание.
- Набор тестов не запускается целиком из-за одного неверного импорта.
- Оценка расстановки по матрице времён прибытия на numpy в 322 раза быстрее расчёта по графу и даёт те же значения. Матрица через `scipy` строится в 19 раз быстрее, чем через `get_atm`; для Красноярска — за 13 секунд.
- Точный решатель находит доказанный оптимум MCLP. На целом Красноярске «в лоб» он не справляется, но с сокращённым списком кандидатов решает задачу за 28 секунд и даёт результат на 1,4 пункта выше жадного добавления.
- Жадное добавление отстаёт от оптимума на 1–3 пункта и работает за секунды на целом городе. Генетический алгоритм ни в одном из 40 запусков не дошёл до оптимума и проигрывает жадному добавлению и по качеству, и по времени.
- Индекс прикрытия считается только по объектам, достижимым из оцениваемой расстановки: расстановка, оставляющая полгорода без прикрытия, получает 100 %.
- Ноутбуки с экспериментами для диссертации не запускаются на текущем коде, а имитация отжига в них работала с максимизируемой метрикой, то есть с ошибкой.
- Два примера из документации на текущем коде не работают: один падает, другой молча возвращает пустой результат.

## Как проводился анализ

Прочитан весь код пакетов `genesis`, `fire_units`, `graphs`, `lists`, тесты, конфигурация документации и архив плагина QGIS.

Ноутбуков в репозитории 78. По всем выполнены автоматические проверки: импорты, секреты, абсолютные пути, сохранённые ошибки, фиксация `seed`. Полностью прочитаны ноутбуки документации для пользователей и разработчиков и основные исследовательские (`dis_algorithms*`, `add_check`, `dis_optimums_area`, `lscp_build_for_qgis`, `grid_graphs_test` и восемь небольших). Черновики из `temps/`, архивные ноутбуки, `g_generator` и учебные страницы про `osmnx` и `geopandas` просмотрены по структуре ячеек, не построчно.

Тесты и проверки ошибок запускались в окружении: macOS, Python 3.12, `osmnx` 2.0.0, `networkx` 3.4.2, `pandas` 2.2.2, `numpy` 2.0.2, `geopandas` 1.0.1 — версии взяты из `genesis_env.yaml`. Скрипты, воспроизводящие ошибки, приведены в приложениях.

Вычислительные эксперименты описаны отдельно, в `EXPERIMENTS_GENESIS.MD`, вместе с кодом и ограничениями. Здесь из них взяты только итоговые цифры.

# Часть 1. Результаты анализа

## 1.1. Сильные стороны

- **Модульность.** `BestNodesKoptG` принимает любой алгоритм BLP, `LSCPCommon` — любой MCLP, селектор и критерий остановки, `Hybridization` склеивает алгоритмы в цепочку. Новую метрику или селектор можно добавить, не трогая остальное.
- **Направление оптимизации спрятано в метрике.** Метод `compare` знает, минимизируется метрика или максимизируется, и большинство алгоритмов от этого не зависят.
- **Учтены реальные условия.** Существующие подразделения фиксируются через `static_nodes`, есть маска расчётной области `area` и допуск `appr_val` на слабосвязанные узлы графов OSM.
- **Заделы на скорость.** Матрица времён прибытия с расчётом батчами (`get_atm`) и кэш для неподвижных подразделений (`FirstArrivalUnitCacheState`).
- **Предметные данные.** Скорости пожарных автомобилей из собственного исследования, справочник классов функциональной пожарной опасности с коэффициентами спроса.
- **Обратные вызовы** после эпох и итераций — удобно для прогресса и для плагина QGIS.
- **Проверка входных данных** с понятными сообщениями.
- **Документация** в виде книги с разделами для пользователей и разработчиков, файл соглашений об именах, канбан-доска в репозитории.
- **Генератор синтетических графов** для сравнения алгоритмов в контролируемых условиях.

- `bad_val_in_area=1000` — «плохое» значение только при минимизации; для индекса прикрытия оно окажется лучшим из возможных. Пометка об этом уже есть в `fire_units/mclp.py:53`.
- `genesis/point_selectors.py:39` — исключение создаётся, но не выбрасывается (пропущен `raise`).

- `genesis/lscp.py:322` — `LSCP_ADD` при вызове с `nodes_list` обрезает `self.matrix` навсегда; повторный вызов того же объекта работает с урезанной матрицей.

- `genesis/mclp.py:222` — `BestNodesKoptG` меняет атрибут `appr_val` у переданного ему объекта `best_point_function`; после вызова объект остаётся изменённым.
- `genesis/tools.py:52` — в сообщении об ошибке `{a:type(a)}` вместо `{type(a)}`; само формирование сообщения упадёт с другой ошибкой.
- `graphs/speeds.py:165` — скорость записывается в поле `maxspeed` в метрах в минуту и затирает штатный тег OSM другой единицей измерения.
- `graphs/algorithms.py:79` — `graph_rise_from_gpkg` округляет геометрию во входном датафрейме; если проецирование не удалось, меняются данные вызывающей стороны.

Результат прогона: из 82 тестов 77 прошли, 1 упал, 1 помечен как ожидаемо падающий, 3 не запустились. Прогон занимает около полутора минут.

## 1.6. Производительность

- Каждая оценка решения в `BestNodesGA`, `BestNodesSA` и алгоритмах BLP — полный алгоритм Дейкстры на чистом Python. `nx.multi_source_dijkstra` при этом строит полный путь до каждого узла, а используется из него только первый элемент. На графе Сосновоборска (1935 узлов) одна оценка занимает 4,65 мс.
- Время генетического алгоритма почти целиком состоит из этих оценок: запуск с параметрами из документации делает 1550 оценок, 1550 × 4,65 мс = 7,2 с — столько он и работает.
- Готовый `ArrivalTimeMatrixState` ускоряет оценку только в 3,2 раза: его время уходит на операции pandas. Та же оценка на numpy быстрее расчёта по графу в 322 раза.
- `get_atm` считает матрицу через `networkx`: 7,6 с на Сосновоборске против 0,39 с через `scipy`.
- Генетический алгоритм пересчитывает одинаковых особей: стартовая популяция — N копий одного решения, каждая оценивается отдельно; элита переоценивается каждую эпоху.
- `BestNodeMonkey` на каждом глобальном прыжке заново переводит граф в GeoDataFrame и перепроецирует его (`genesis/best_points.py:717-719`). Два теста этого алгоритма занимают по 20 секунд — половину всего времени прогона.
- `BestNodesKoptG` копирует подграф на каждое подразделение в каждой итерации.
- `get_atm` склеивает матрицу через `pd.concat` в цикле.
- `CoverIndex` считает долю циклом Python по элементам.

### По чтению кода (данные недоступны, запуском не проверялось)

**Эксперименты для диссертации** (`dis_algorithms.ipynb`, `dis_algorithms copy.ipynb`, `dis_algorithms IPV5.ipynb`):

- Имитация отжига запускается с максимизируемой метрикой: в ранних версиях это `Demand` (`comp_func=max`), в `IPV5` — `CoverIndexValue`. Формула вероятности перехода в `genesis/mclp.py` не менялась с 05.07.2024, ноутбуки появились 13.08.2024. Значит, результаты SA в сравнении алгоритмов BLP и MCLP получены с ошибкой № 1 и требуют пересчёта.
- В сравнении MCLP каждый стохастический алгоритм запускается по одному разу на район, без фиксации `seed`.

## 2.2. Производительность

Цифры в этом разделе измерены; постановка и код — в `EXPERIMENTS_GENESIS.MD` (эксперименты 1 и 4).

**Оценивать решения по матрице на numpy.** Это главный рычаг.

Сейчас метаэвристики на каждую оценку запускают алгоритм Дейкстры. Если один раз посчитать матрицу «объект × кандидат», оценка любой расстановки становится минимумом по нескольким столбцам.

| Способ оценки одной расстановки | Время | Ускорение |
|---|---|---|
| `FirstArrivalUnitState` — по графу (как сейчас) | 4,65 мс | — |
| `ArrivalTimeMatrixState` — матрица в pandas | 1,44 мс | в 3,2 раза |
| Матрица в numpy | 0,014 мс | в 322 раза |

Значения метрик во всех трёх вариантах совпадают. Существующий `ArrivalTimeMatrixState` для этой роли не годится: он использует малую долю возможного выигрыша. Нужен новый класс состояния, который хранит матрицу как массив numpy вместе с соответствием «узел → номер столбца», а имя первого прибывающего подразделения вычисляет только по запросу.

Дополнительно при перестановке одного подразделения можно не пересчитывать всё: достаточно хранить для каждого объекта лучшее и второе по времени подразделение.

**Строить матрицу через `scipy`.** `scipy.sparse.csgraph.dijkstra` выполняет тот же расчёт на C и поддерживает ограничение по времени (`limit`). На Сосновоборске это 0,39 с против 7,6 с у `get_atm` — в 19 раз быстрее при расхождении значений порядка 10⁻¹⁴. Матрица покрытия для Красноярска (19 519 объектов × 32 082 кандидата, порог 10 минут) построена за 13 секунд.

**Группировать здания по узлам (Н6).** Сейчас `get_atm` запускает расчёт для каждого здания. Достаточно одного расчёта на узел с весом, равным числу зданий. Для Красноярска 68 815 зданий превращаются в 19 519 объектов — задача в 3,5 раза меньше без потери точности.

**Хранить матрицу разреженно.** Для задач покрытия нужны только пары в пределах порога прибытия. У Красноярска это 71,1 млн пар из 626 млн возможных (11,3 %).

## 2.3. Алгоритмы

**Точное решение задач покрытия.** MCLP и LSCP — задачи целочисленного линейного программирования. Пусть `x_j = 1`, если в кандидате `j` размещено подразделение, `y_i = 1`, если объект `i` прикрыт, `N_i` — кандидаты, из которых до объекта `i` успевают за пороговое время, `w_i` — вес объекта.

LSCP (минимум подразделений при полном прикрытии):

```
min  Σ_j x_j
при  Σ_{j ∈ N_i} x_j ≥ 1   для каждого объекта i
```

MCLP (максимум прикрытия при `p` подразделениях):

```
max  Σ_i w_i · y_i
при  y_i ≤ Σ_{j ∈ N_i} x_j   для каждого объекта i
     Σ_j x_j = p
```

Существующие подразделения задаются условием `x_j = 1`. Множества `N_i` получаются из матрицы покрытия. Решатель — HiGHS, доступный через `scipy.optimize.milp`.

Что показали измерения (MCLP, эксперименты 2 и 4):

| Задача | Точный решатель | Жадное добавление |
|---|---|---|
| Сосновоборск, 1 935 × 1 935, от 2 до 8 подразделений | оптимум за 0,5 с | совпадает с оптимумом или ниже на 1–2 п. п. |
| Красноярск, выборка 15 000 × 15 000 (25,6 млн пар) | оптимум за 354 с, 13,4 ГБ | ниже на 1,3 п. п. |
| Красноярск целиком, 19 519 × 32 082 (71,1 млн пар) | за 10 минут не решено: 21,6 % | 90,2 % за 1,5 с |
| Красноярск, все объекты × 5 000 кандидатов | оптимум за 28 с: 91,61 % | на полном списке кандидатов — 90,19 % |

Из этого следует, каким должен быть штатный алгоритм:

- объекты группируются по узлам с весами;
- список кандидатов сокращается до нескольких тысяч. Даже случайной выборки из 5 000 хватило, чтобы превзойти жадное добавление на полном списке; осмысленный отбор (по классу дорог, по пригодным участкам) должен быть не хуже;
- решатель запускается с лимитом времени. Если оптимум не найден, возвращается результат жадного добавления, а не то, на чём решатель остановился;
- жадное решение передаётся решателю как стартовое. Через `scipy.optimize.milp` это невозможно, нужен прямой интерфейс HiGHS (`highspy`);
- время решения нельзя предсказать по размеру задачи: вариант с 2 000 кандидатов считался в 12 раз дольше, чем с 5 000.

Предел применимости «в лоб» на проверенных данных — около 25 миллионов пар «объект — кандидат». Выше него решатель за 10 минут не дал ни решения, ни полезной оценки сверху: граница осталась около 100 %. Поэтому для больших задач оценку сверху нужно получать отдельным методом, например релаксацией Лагранжа; это не проверялось.

Точное решение даёт эталон для эвристик: раньше не было способа узнать, насколько их результат далёк от оптимума. Ограничение: формулировка подходит для метрик покрытия. Для среднего времени прибытия (задача p-медианы) модель крупнее; на этих данных она не проверялась.

**Жадное добавление — вариант по умолчанию.** Измеренное отставание от оптимума — от 0 до 3 процентных пунктов на обоих графах и при числе подразделений от 2 до 40, время — от сотых долей секунды до 1,5 с на целом Красноярске. Теоретическая гарантия для него — не хуже 63 % от оптимума. Отставание стоит сокращать шагом замены после жадного этапа: убрать одну точку, поставить другую, принять обмен при улучшении. «Ленивый» вариант даёт тот же результат за меньшее число пересчётов.

**Обменный локальный поиск для среднего времени.** `BestNodesKoptG` по сути является алгоритмом Маранзаны: каждое подразделение переставляется в лучшую точку своей зоны. Алгоритм Тейца–Барта для p-медианы обычно даёт лучшие решения и по матрице считается быстро. Его стоит добавить как отдельный алгоритм и как финальную доводку. На данных проекта это не проверялось.

**Место метаэвристик.** Для метрик покрытия генетический алгоритм в нынешнем виде уступает и точному решателю, и жадному добавлению. На Сосновоборске с параметрами из документации он ни в одном из 40 запусков не достиг оптимума; среднее отставание — от 1,7 до 7,8 п. п. и растёт с числом подразделений, а время запуска — 7,2 с против сотых долей секунды у жадного добавления. Область метаэвристик — метрики, которые не записываются линейно, и пользовательские постановки. С большим числом эпох результат, вероятно, улучшится; это не проверялось.

**Города крупнее Красноярска.** Число пар растёт примерно пропорционально числу объектов: на один объект Красноярска приходится в среднем 3 640 кандидатов в пределах 10 минут. Сокращения кандидатов для города в несколько раз больше, скорее всего, уже не хватит. Тогда задача решается по районам с согласованием стыков. Это оценка, не измерение.

**Доработка метаэвристик** помимо исправления ошибок:

- разнообразная стартовая популяция в генетическом алгоритме вместо N копий одного решения;
- шкала температуры в отжиге, учитывающая масштаб метрики (минуты и проценты сейчас обрабатываются одинаково);
- параметр `seed` у всех стохастических алгоритмов для воспроизводимости расчётов;
- ограничение числа итераций в `LSCPCommon`.

**Требования к ноутбукам экспериментов:**

- `seed` фиксируется; стохастические алгоритмы запускаются по несколько десятков раз, в таблицу идут среднее и разброс, а не один запуск;
- таблицы результатов (`blp.csv`, `mclp.csv`, `lscp.csv`) хранятся рядом с ноутбуком или в отдельном архиве данных, а не только на рабочем компьютере;
- эталоном служит точное решение (раздел 2.3) там, где оно возможно, и полный перебор — для BLP;
- у каждого столбца таблицы один смысл для всех алгоритмов.

**Пересчитать сравнение алгоритмов** после исправления ошибки № 1: результаты SA в `dis_algorithms*` получены с неверным правилом перехода.

**Запретить запись в `tests/data` из ноутбуков**; тестовые данные формируются отдельным скриптом.

**Термины гибридизации.** «Бустинг» и «стекинг» заменить названиями, соответствующими реализации: последовательная гибридизация (цепочка) и выбор лучшего из независимых запусков. Старые значения параметра оставить как синонимы.

## 2.8. Порядок работ

Четыре этапа; каждый следующий опирается на предыдущий.

**Этап 1. Привести основу в порядок.**

Без этого этапа ускорения строятся на коде, которому нельзя доверять.

**Этап 2. Новое вычислительное ядро.**

- Объект «задача», отделённый от графа (раздел 2.4).
- Построение матрицы через `scipy`, группировка зданий по узлам, разреженное хранение.
- Оценка расстановки на numpy.
- Явное направление метрики, сигнатуры без поглощения лишних аргументов.

Этап небольшой по объёму кода, а эффект измерен: в сотни раз на оценке расстановки и в десятки на построении матрицы. Все существующие алгоритмы ускоряются сразу, и на эту основу опирается весь следующий этап.

**Этап 3. Алгоритмы.**

- Жадное добавление с шагом замены — вариант по умолчанию.
- Точный решатель как штатный алгоритм: с сокращением кандидатов, лимитом времени, запасным вариантом и стартовым решением.
- Оценка сверху для задач, где оптимум недоступен.
- Метаэвристики: исправить, перевести на быструю оценку и оставить для метрик, которые не записываются линейно.
- В документации — правило выбора алгоритма: метрика покрытия и примерно до 25 миллионов пар — точный решатель; задача больше — сократить кандидатов либо жадное добавление; метрика нелинейная — метаэвристики.

**Этап 4. Масштаб и воспроизводимость.**

- Декомпозиция по районам с параллельным расчётом для городов крупнее Красноярска.

- Компилируемые ядра — по результатам профилирования.
- Объединение пакетов, устранение дублирования, очистка репозитория, публикация документации.

**Что в план не заложено как решённое.** Две задачи на данных проекта не проверялись: среднее время прибытия (p-медиана) и LSCP — минимальное число подразделений для заданного прикрытия. Они стоят в списке следующих проверок в `EXPERIMENTS_GENESIS.MD`.

# Приложение 1. Воспроизведение ошибок в алгоритмах

Запускается из каталога `work/genesis`. Ошибка № 6 в скрипт не включена — она видна по коду.

```python
import random

import networkx as nx
import pandas as pd

from genesis.best_points import BestNodeHillClimbing, BestNodesFull
from genesis.hybridisation import Hybridization
from genesis.lscp import LSCP_ADD
from genesis.mclp import BestNodesGA, BestNodesKoptG, BestNodesSA
from genesis.metrics import ArrivalTime, CoverIndex
from genesis.point_selectors import RandomNodesSelector
from genesis.states import FirstArrivalUnitState
from graphs.algorithms import generate_grid_graph

# Сетка 8x8, время проезда каждого ребра 2 минуты
G = generate_grid_graph(8, 8, step=1000, speed=30, add_geometry=False)
state = FirstArrivalUnitState()


def check(title, func):
    try:
        print(f'{title}: {func()}')
    except Exception as e:
        print(f'{title}: {type(e).__name__}: {e}')


# № 1. Отжиг: вероятность принять худшее решение при максимизации (ИП 80 % -> 50 %)
sa = BestNodesSA(state, CoverIndex(5), RandomNodesSelector())
check('1. SA, вероятность перехода', lambda: sa._get_transition_probability(50 - 80, 0.5))

# № 2. ГА: одинаковая приспособленность всей популяции
ga = BestNodesGA(state, ArrivalTime(), RandomNodesSelector(), population_size=8, epochs=5, mutation_rate=0)
check('2. ГА, равная приспособленность', lambda: ga(env=G, dynamic_nodes={0: 'a', 1: 'b'}))


# № 3. ГА: потеря подразделений при скрещивании
def ga_sizes():
    sizes = set()
    ga = BestNodesGA(state, ArrivalTime(), RandomNodesSelector(), population_size=12, epochs=25)
    fit = ga._fit_function
    ga._fit_function = lambda env, nodes, area=None, **kw: (sizes.add(len(nodes)), fit(env, nodes, area, **kw))[1]
    random.seed(3)
    ga(env=G, dynamic_nodes={0: 'a', 1: 'b', 2: 'c', 3: 'd'})
    return f'задано 4 подразделения, размеры особей: {sorted(sizes)}'


check('3. ГА, скрещивание', ga_sizes)

# № 4. Hybridization с областью расчета
area = pd.Series(True, index=list(G.nodes()))
kopt = BestNodesKoptG(state, ArrivalTime(), BestNodeHillClimbing(state, ArrivalTime()), iterations=2)
hyb = Hybridization(state, ArrivalTime(), [kopt])
check('4. Hybridization с area', lambda: hyb(env=G, dynamic_nodes={0: 'a', 1: 'b'}, area=area))

# № 5. LSCP_ADD без критерия остановки, но со статическими узлами
matrix = pd.DataFrame({n: pd.Series(nx.single_source_dijkstra_path_length(G, n, weight='travel_time'))
                       for n in G.nodes()})
add = LSCP_ADD(state_function=state, matrix=matrix, metric_function=CoverIndex(6), ip_val=6)
check('5. LSCP_ADD без stop_case_function', lambda: add(env=G, static_nodes={0: 'ПСЧ-1'}))

# № 7. Полный перебор при нулевой метрике во всех узлах
check('7. BestNodesFull, метрика 0', lambda: BestNodesFull(state, CoverIndex(0.5))(env=G))
```
